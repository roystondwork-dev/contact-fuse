# Documentation

Good documentation is how an open-source project gains contributors and keeps users' trust. This document defines what we document, where, in what style, and when — including when an Architecture Decision Record (ADR) is required.

## 1. Where documentation lives

| Audience               | Location                                              | Examples                                     |
| ---------------------- | ----------------------------------------------------- | -------------------------------------------- |
| Users                  | `README.md`, `docs/guides/`                           | install, Google Cloud setup, troubleshooting |
| Contributors           | `CONTRIBUTING.md`, `docs/standards/`, `docs/process/` | coding standards, git workflow               |
| Architects / reviewers | `docs/architecture/`, `docs/adr/`                     | system overview, decisions                   |
| Product & design       | `docs/product/`, `docs/design/`                       | roadmap, design system                       |
| AI assistants          | `CLAUDE.md`, `AGENTS.md`, `.claude/skills/`           | project rules for coding agents              |
| API consumers          | TSDoc in code, generated OpenAPI                      | `@contact-fuse/core` exports                 |
| Release notes          | `CHANGELOG.md` (generated by Changesets)              | —                                            |

The index of all docs is [docs/README.md](../README.md). Every new doc must be linked from it.

## 2. Docs ship with the code

- **A PR that changes behaviour updates the docs in the same PR.** Reviewers block PRs where docs are stale (part of the [definition of done](../process/definition-of-done.md)).
- User-visible changes need a Changeset entry describing them in user language.
- New error codes → [error code catalog](error-handling-and-logging.md#3-error-code-catalog). New settings → user guide + [glossary](../product/glossary.md) if a new term. New table → [database.md](database.md) and [data-model.md](../architecture/data-model.md).
- Broken internal links fail CI (markdown link check).

## 3. Architecture Decision Records

ADRs record **why** we made a significant decision, so future contributors don't relitigate it or undo it by accident.

**Write an ADR when a change:**

- adds or replaces a framework, database, major library, or build tool;
- changes a package boundary or the provider interface;
- changes security, privacy, or data-handling behaviour (tokens, telemetry, what is stored);
- changes the safety model of merges (backups, undo, deletion defaults);
- introduces a breaking change to the API, DB schema (destructive), or settings format;
- is hard to reverse or affects multiple packages.

**No ADR needed** for bug fixes, refactors within a module, adding a field, or routine dependency updates.

Process:

1. Copy [adr/template.md](../adr/template.md) to `docs/adr/NNNN-kebab-title.md` (next number).
2. Status `Proposed`; open a PR. Discussion happens on the PR.
3. On merge, status becomes `Accepted`. Add it to the index in [adr/README.md](../adr/README.md).
4. ADRs are immutable once accepted. To change a decision, write a new ADR and mark the old one `Superseded by NNNN`.

## 4. Code documentation (TSDoc)

- **All exports from a package's `index.ts`** (core, providers) have a TSDoc comment: what it does, parameters that aren't obvious, return value, thrown error codes, and an example for non-trivial APIs.
- Internal functions get a comment only when the **why** is not obvious.
- Use TSDoc tags: `@param`, `@returns`, `@throws`, `@example`, `@see`, `@deprecated` (with replacement).

/**
 * Scores how likely two contacts are the same person.

## 5. Writing style

- **Plain, direct English.** Many contributors and users are non-native speakers. Short sentences, common words, active voice.
- **Second person, present tense:** "Run `pnpm check`", not "The developer should run…".
- **Lead with the answer.** Purpose paragraph first; details after.
- **Show, don't describe:** concrete commands, code, and examples beat paragraphs.
- **Use glossary terms exactly** ([glossary.md](../product/glossary.md)).
- **macOS, Windows, Linux:** when commands differ, show all three or note the difference. Don't assume the reader knows platform-specific tooling.
- **No PII in examples.** Use `example.com` emails and fake names, as in [testing.md](testing.md#5-test-data-synthetic-only).
- User-facing guides follow the voice in [content-style-guide.md](../design/content-style-guide.md).

## 6. Markdown conventions

- File names kebab-case `.md` (root community files are UPPER_CASE).
- One `# H1` per file, matching the document's title; sentence-case headings.
- A one-paragraph purpose statement under the H1. Add a table of contents for docs with more than ~5 sections.
- Relative links between docs (`../architecture/overview.md`), never absolute GitHub URLs.
- Fenced code blocks always declare a language (` ```ts `, ` ```bash `).
- Diagrams in Mermaid code blocks (rendered by GitHub), not images, so they stay editable and diffable.
- Wrap nothing manually — one paragraph per line; Prettier formats tables.
- Use tables for comparisons and reference data; use ✅/❌ for do/don't examples.
